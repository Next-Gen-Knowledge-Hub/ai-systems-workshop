# Deploying agents and agentic systems

How people consume the agent decides where it runs. A voice agent in the page wants the model close: WebRTC or a WebSocket, interruptible speech, token streaming, and tools that stay simple or get proxied through your server. After sign-in, mint a short-lived client secret. Never ship a provider key to the browser.

A task that fits one round trip, an image, a summary, a lookup, wants a synchronous API another app or agent can call. A job that outruns an HTTP timeout wants a queue and a worker that can retry and limit concurrency. If you are unsure, start with the API, move the conversational hot path to the edge, and push slow tools onto event-driven workers. The experience sets the latency you are allowed to spend.

A front door faces the user and routes intent to specialists. Those workers may use different wires, because their latency differs. Keep the door thin, and keep the control inside the workers.

- **Docker and Compose.** An agent is a natural small service: its own dependencies, easy to swap and version. A container freezes that runtime. Compose brings up the web UI, the workers, and the tool sidecars together. A tunnel is enough for a proof of concept. A polished release runs where you operate it.
- **The three wires.** Full-duplex WebRTC or WebSockets for speech and live canvases. HTTP with server-sent events when you want a stream you can proxy, log, and cache, including MCP calls. A bus such as Redis, NATS, or Kafka when the person should keep talking while a slow tool finishes and posts the result back. Local MCP can still use STDIO.
- **State, memory, and idempotency.** Recent turns live in fast storage such as Redis or Postgres. Lasting facts live in a shared index any worker can read. A forecast for a given place and time can be stored and served again. A message that leaves the building has to happen once. Shape every safe tool so a retry or a replay returns the earlier result instead of repeating the act.
- **Release engineering.** Prompts, tool schemas, safety switches, and model choices are software. Version them. Promote through offline tests, shadow traffic, a small canary, then everyone, and roll back when the service level slips. Pin the exact model and tool endpoint on each turn so an incident can be replayed.
- **Seeing it, bounding it, paying for it.** Trace the path from the screen through the gateway, the agent, the tools, and the model, with a session id and a turn id. Watch latency, tool success, tokens, grounding, and whether the task finished. Put a time budget on every critical path and fall back when it blows: a smaller model, a plainer answer, text when speech is down. Trip a breaker when a tool keeps failing. Route by intent, and keep a strong model on the router until a cheaper one has been measured. Trim stale context. Cache stable prompts and deterministic results. Fewer tokens are usually a faster reply, and a cheap run is a win only next to the work it replaces.
- **Threat model, identity, and policy.** Name the assets first: keys, tool credentials, data read, data written, logs, personal data. Then the surfaces: browser, gateway, runtime, tool servers, the model vendor, and storage. Pass the user's own authority into every call. Inject secrets at runtime, keep them out of images and out of the prompt, and rotate them. Sandbox tools, lock the filesystem to known paths, default-deny the network, and cap memory, CPU, and time. Treat user text and retrieved pages as untrusted data. Put the system prompt and the tool contracts above anything found in a document. Bind arguments to a schema. Put a person on send, pay, and code execution.

The smallest runtime that meets the latency, wrapped in traces, budgets, and a threat model you could draw, is how a demo becomes a system you can leave running.
